# v1.5.1 — Skill `backlog-tareas` incluida en gtt

**Fecha:** 2026-10-05
**Tipo:** Patch (decisión del mantenedor: funcionalidad nueva que se mantiene en la línea 1.5)
**Versión anterior:** v1.5.0

---

## 1. Solicitud

Compartir con los compañeros la skill `backlog-tareas` de Claude Code (la que
convierte los hallazgos de `gtt backlog scan` en tareas para Jira) **sin tener
que enviarla a mano cada vez que cambia**, cubriendo dos escenarios:

1. Un compañero que usa una versión anterior de `gtt` solo tiene que actualizar
   `gtt`: la skill llega con la actualización y queda lista para usar.
2. Un compañero que ya tiene la skill recibe las mejoras al actualizar `gtt`,
   comparando su copia con la nueva.

Y la pregunta de fondo: **qué pasa si un usuario modifica su skill.**

---

## 2. Motivación

| Problema | Daño real |
|---|---|
| La skill se reparte copiando una carpeta | Cada mejora implica volver a enviarla; cada compañero queda en una versión distinta sin saberlo |
| La skill lee el JSON de `gtt backlog scan` | Una skill nueva con un `gtt` viejo (o al revés) puede leer campos que no existen y proponer tareas sin el filtro que el usuario pidió |
| Nada distingue "versión vieja" de "versión editada" | Actualizar a ciegas borra los cambios del usuario; no actualizar deja a todos atrás |
| La skill tenía nombres de repos, módulos y clases de la empresa | Embebida tal cual, quedaría dentro del binario que se publica en GitHub Releases (P-008) |

## 3. Diseño técnico

### 3.1 La skill viaja dentro del binario

`internal/skill/backlog-tareas/` (`SKILL.md`, `plantilla.md`) se embebe con
`//go:embed`. La skill y el binario que genera los reportes salen siempre de la
misma versión: no pueden desfasarse.

**El escenario 1 no necesita cambios en versiones anteriores.** `gtt update` solo
reemplaza el binario y termina; quien instala la skill es el binario **nuevo**,
en su primer comando. Por eso un `gtt` < v1.5.1, que no sabe que la skill
existe, la recibe igual con su `gtt update` de siempre.

### 3.2 Manifiesto: versión vieja frente a versión editada

Al instalar, `gtt` escribe `.gtt-skill.json` junto a la skill con la versión de
`gtt` que la instaló y el SHA-256 de cada archivo. Al arrancar compara tres
cosas: la skill embebida, la del disco y el manifiesto (`skill.Diagnose`, pura y
con tests).

| Estado | Cómo se detecta | Qué hace `gtt` al arrancar |
|---|---|---|
| No instalada | Sin archivos ni manifiesto | Pregunta **una vez**; un "no" se recuerda en `~/.config/gtt/skill_state.json` |
| Al día | Disco = embebida | Nada (rehace el manifiesto si falta o está desactualizado) |
| Versión anterior sin tocar | Disco = manifiesto ≠ embebida | Actualiza y avisa en una línea |
| Editada por el usuario | Disco ≠ manifiesto | **No la toca.** Deja la oficial al lado como `<archivo>.nuevo` y avisa **una vez por versión** |
| Copia a mano distinta | Sin manifiesto y disco ≠ embebida | Igual que editada |
| Instalada por un `gtt` más nuevo | Versión del manifiesto > la propia | Nada: nunca se rebaja |

Se compara por hash y no solo por número de versión: la versión dice quién la
instaló, el hash dice si alguien la cambió después.

### 3.3 Qué pasa si un usuario modifica su skill

No se puede impedir (es su equipo y su `~/.claude`); se puede **detectar, no
pisar y dar salida**:

- `gtt skill status` — estado y archivos cambiados.
- `gtt skill diff` — cambios frente a la oficial, con `git diff --no-index`
  (ruta de git resuelta con `exec.LookPath`, P-005).
- `gtt skill reset` — vuelve a la oficial guardando `<archivo>.respaldo-<fecha>`.
- `gtt skill install` — instalación explícita; se niega si hay cambios locales.

Y un lugar legítimo para lo propio: **`local.md`**, en la carpeta de la skill.
`gtt` lo crea una vez desde una plantilla y **nunca lo modifica**; no entra en el
manifiesto. La skill lo lee primero y lo que diga tiene prioridad sobre sus
valores por defecto (equivalencia de puntos, formato de rama, estándares y
comandos de prueba por repo, nombres de módulos). Así nadie necesita editar
`SKILL.md`, y un ajuste que sirve a todos entra en la oficial en la versión
siguiente.

### 3.4 Generalización (P-008)

La skill embebida no contiene nombres de repos, módulos, clases, la clave del
proyecto en Jira ni rutas de skills de estándares internas. Los ejemplos usan un
dominio genérico (pedidos, descuentos) y todo lo del equipo pasó a `local.md`.

### 3.5 Cuándo corre la sincronización

Solo en ejecuciones interactivas de un binario publicado (`shouldSyncSkill` en
`main.go`):

- stdout y stdin son terminal (nunca pregunta en pipes ni CI);
- la versión no es `dev`: `go run` no sobrescribe la skill del desarrollador con
  trabajo en curso (los subcomandos `gtt skill ...` sí funcionan en `dev`);
- no corre en `skill`, `update`, `version`, `help` ni con `-h`;
- si no existe la carpeta de Claude Code (`$CLAUDE_CONFIG_DIR` o `~/.claude`),
  no hace nada: no hay quién use la skill.

Un error al sincronizar se muestra como advertencia y nunca hace fallar el
comando que pidió el usuario.

## 5. Cómo verificar

```bash
cd ~/go/src/deploy-doc
export PATH="/usr/local/go/bin:$PATH"
go vet ./... && GOOS=windows go vet ./... && gofmt -l . && go test ./...
bash .claude/skills/version-check/check.sh
```

Subcomandos con `go run`, sobre una carpeta temporal (nunca sobre la skill real):

```bash
T=$(mktemp -d); export CLAUDE_CONFIG_DIR=$T/.claude; mkdir -p $CLAUDE_CONFIG_DIR
go run . skill                    # No está instalada
go run . skill install            # crea SKILL.md, plantilla.md, local.md, .gtt-skill.json
echo x >> $CLAUDE_CONFIG_DIR/skills/backlog-tareas/SKILL.md
go run . skill status             # Tiene cambios locales: SKILL.md
go run . skill install            # se niega
go run . skill diff               # muestra "+x"
go run . skill reset              # restablece y deja SKILL.md.respaldo-<fecha>
```

**Sincronización automática** (necesita un binario publicado y una terminal; no
corre con `go run`): después de liberar v1.5.1, en un equipo con `gtt` v1.5.0 y
Claude Code:

1. `gtt update` y luego cualquier comando (`gtt project list`) → pregunta si
   instalar la skill.
2. Editar `SKILL.md` y simular una versión siguiente → aparece `SKILL.md.nuevo` y
   el aviso sale una sola vez.

## 6. Notas de compatibilidad

- **Quien ya tenía la skill copiada a mano** queda como "copia a mano distinta":
  `gtt` no la toca y deja `SKILL.md.nuevo`. Para pasarse a la gestionada: mover
  las convenciones propias a `local.md` y correr `gtt skill reset` (deja respaldo).
- **Comando nuevo `skill`.** Ningún comando ni flag existente cambia.
- **Archivos nuevos en `~/.config/gtt/`:** `skill_state.json`, solo si el usuario
  responde que no a la instalación.
