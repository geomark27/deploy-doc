# v1.4.2 — Ayuda en dos niveles, `-h` que nunca ejecuta y verificación de versiones

**Fecha:** 2026-10-02
**Tipo:** Patch
**Versión anterior:** v1.4.1

---

## 1. Solicitud

Tres pedidos sobre la misma base.

**Ayuda más específica.** El usuario no encontraba cómo pedir el detalle de un
comando ("¿hay un `gtt help-scan`?") y propuso organizar la ayuda: una general
con cada opción disponible y, para el detalle, un flag más, como se hizo con
`backlog`.

**Ayuda de `backlog scan`.** Con v1.4.1 no quedaba claro si había que tocar el
`config.yaml`, desde qué carpeta se ejecuta ni para qué sirve `--json`.

**Versiones.** Tras v1.4.1 se pidió actualizar bien la bitácora y agregar una
skill que, al terminar cada tarea de un agente, verifique el estado de las
versiones.

---

## 2. Motivación

| Problema | Daño real |
|---|---|
| `gtt help` era una sola pantalla con los flags de todos los comandos | Para encontrar un flag de `qa` había que leer los de `generate`, `fetch` e `init`. `gtt help <comando>` ignoraba el argumento |
| `gtt update -h` y `gtt init -h` ejecutaban el comando | `update -h` actualizaba el binario e `init -h` abría el asistente, que puede sobrescribir la config, cuando solo se pedía ayuda |
| El ejemplo `gtt backlog scan -o C:\reportes\backlog.json` fallaba | Con un proyecto de dos repos, `-o` exige una carpeta: el ejemplo de la propia ayuda daba error |
| `--dry-run` de `generate` y `qa` no aparecía en ninguna ayuda | Un flag útil y seguro solo se descubría leyendo la guía o el código |
| Un `make release` desde una rama de feature | Tres releases (v1.3.1, v1.4.0, v1.4.1) para un mismo cambio; la entrada v1.4.0 de la bitácora recibió contenido de la versión siguiente |
| El paso 5 de `/pre-release` ("Verificar versión") leía `internal/build/version.go` | Ese archivo siempre dice `"dev"` (la versión real se inyecta con `-ldflags`), así que el paso nunca podía detectar nada |

## 3. Diseño técnico

### 3.1 Ayuda en dos niveles

| Comando | Qué muestra |
|---|---|
| `gtt help` (o `--help`, `-h`, `gtt` solo) | Índice: comandos agrupados por uso (Configuración, Documentación en Atlassian, Backlog técnico, Mantenimiento), una línea cada uno, ejemplos rápidos y dónde está el `config.yaml` |
| `gtt help <comando>` / `gtt <comando> -h` | Ayuda detallada: flags con sus valores por defecto, prioridades, configuración y ejemplos |

Todo lo que mostraba la ayuda anterior se conservó, repartido en la ayuda de
cada comando (`printInitUsage`, `printGenerateUsage`, `printQAUsage`,
`printFetchUsage`, `printUpdateUsage`, más las existentes de `project` y
`backlog`). Vive en `cmd/help.go`; `root.go` queda con el router y el parseo de
flags. Funciona con los alias (`gtt help g`, `gtt f -h`) y con subcomandos
(`gtt project add -h`, `gtt backlog scan -h`).

`commandHelp` mapea cada comando y alias a su ayuda. `TestEveryCommandHasHelp`
falla si un comando de `commands` no tiene ayuda o si `commandHelp` nombra uno
que no existe: un comando nuevo sin ayuda no llega a `main`.

### 3.2 `-h` se resuelve antes de ejecutar

`Execute` revisa `-h` / `--help` en los argumentos **antes** de llamar al
comando. Hacerlo dentro de cada comando dejaba fuera justo a los que ignoran
sus flags (`init`, `update`), que son los que tienen efectos. Un único punto de
control evita que un comando nuevo repita el olvido.

### 3.3 Ayuda de `backlog scan`

Explica qué analiza y desde dónde (cualquier carpeta: las rutas salen del
proyecto), cada flag con su valor por defecto, los detectores, cómo activar
`sin-test` con la ruta del `config.yaml` en el formato del sistema
(`%USERPROFILE%\.config\gtt\config.yaml` en Windows) y ejemplos comentados.
El ejemplo con archivo de salida pasa a `-r backend -o <archivo>`, que es
válido; la guía muestra además `-o <carpeta>` para dos repos.

El ejemplo de la ayuda general cambia de `--json` (para herramientas) a `-o`,
que es lo que usa una persona.

### 3.4 Skill `version-check`

`.claude/skills/version-check/` con un `SKILL.md` (cuándo usarla y cómo
interpretar el resultado) y un script de solo lectura, `check.sh`. El script
reproduce el cálculo del `Makefile` (`git describe --tags --abbrev=0` desde
`HEAD`) y comprueba:

| Sección | Qué verifica |
|---|---|
| Rama y working tree | Que se libere desde `main`, sincronizado con `origin`; avisa de cambios sin commit, que `git add -A` metería en el commit de release |
| Tags | Que `HEAD` contenga el último tag; tags fuera de `main` o que comparten commit sin nota en la bitácora |
| GitHub Releases | Que el release "Latest" coincida con el último tag y que cada tag tenga release publicado (`gtt update` solo ve releases) |
| Próxima versión | Lo que daría `make release`, `-minor` y `-major`, con el criterio de cuándo usar cada uno |
| Bitácora | Que exista la entrada de la próxima versión, que su "Versión anterior" sea la base real, que esté en el índice, y que no se haya agregado contenido a entradas ya publicadas |
| gtt instalado | La versión del binario instalado frente al último release |

Es un script, y no instrucciones sueltas, para que el resultado sea el mismo
lo corra un agente o una persona. `CLAUDE.md` indica correrlo al terminar
cualquier tarea que modifique el repo, y el paso 5 de `/pre-release` lo usa en
lugar de leer `version.go`.

No corre `make release*`, no crea ni borra tags y no hace commit: decide y
ejecuta el usuario.

### 3.5 Registro de v1.3.1, v1.4.0 y v1.4.1

Los tres tags publican el mismo cambio. `v1.3.1` y `v1.4.0` apuntan al mismo
commit, `release: v1.3.1`, creado en `feat/backlog-scan`; `v1.4.1`, al merge del
PR #6 en `main`. **v1.4.1 es la versión de referencia.** No se borra ningún tag:
ya fueron publicados y alguien pudo haberlos descargado. La entrada `v1.4.0.md`
recibe solo una nota aclaratoria y el índice de la bitácora los registra.

## 5. Cómo verificar

```bash
cd ~/go/src/deploy-doc
export PATH="/usr/local/go/bin:$PATH"

# 1. Estático y tests
go vet ./... && GOOS=windows go vet ./... && gofmt -l . && go test ./...

# 2. Versiones — antes de liberar debe quedar sin bloqueantes
bash .claude/skills/version-check/check.sh
```

```powershell
# 3. Ayuda en dos niveles
gtt help                   # índice corto
gtt help g                 # = gtt g -h = gtt generate --help
gtt f -h
gtt project add -h
gtt backlog scan -h

# 4. -h nunca ejecuta el comando
gtt update -h              # muestra la ayuda; NO descarga ni reemplaza el binario
gtt init -h                # muestra la ayuda; NO abre el asistente

# 5. Ejemplo de -o de la ayuda de backlog
gtt backlog scan -r backend -o C:\reportes\backlog.json
```

## 6. Notas de compatibilidad

- **Sin cambios en flags, comandos ni config.**
- **`gtt help`** muestra un índice más corto; el detalle que antes estaba ahí
  está en `gtt help <comando>`.
- **`gtt <comando> -h` / `--help`** muestra la ayuda y no ejecuta el comando. Antes,
  en `update` e `init`, ejecutaba el comando.
- **v1.3.1 y v1.4.0** siguen publicados; contienen lo mismo que v1.4.1.
